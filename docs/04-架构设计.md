## 一、架构决策汇总

### 1.1 两个原方案的统一

项目启动时存在两个并行的重构方案，最终统一为三层架构：

| 原方案 A（分层） | 原方案 B（节点） | **统一架构定位** |
|-----------------|-----------------|-----------------|
| 存储引擎层 | ClickHouse/MySQL Dialect | **内置于 DatabaseNode** |
| 数据访问层 | DatabaseNode | **DatabaseNode** |
| 业务逻辑层 | FactorNode/OperatorNode | **FactorNode/TransformNode** |
| 符号计算层 | （方案 B 未明确） | **FactorNode 的内部实现** |
| AI 增强层 | StrategyGenerator | **元节点（Meta-Node）** |
| 交互层 | （方案 B 未考虑） | **UINode + Streamlit 分离** |

### 1.2 最终决策总结表

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 两个原方案关系 | ✅ 统一为三层架构 | 分层架构是节点分类的依据，Pipeline 是组合方式 |
| 控制流实现 | ✅ 三层混合架构 | 专用节点保证可观测性，通用节点提供灵活性 |
| 符号计算暴露方式 | ✅ FactorNode 内部透明实现 | 降低用户认知负担，简化API |
| AI 层定位 | ✅ 元节点（生成 Pipeline） | 发挥 AI 优势，不做数据处理 |
| 组合原语 | ✅ Pipeline/Parallel/Join | 覆盖 99% 的量化场景，简单通用 |
| 存储层抽象 | ✅ 内置于 DatabaseNode | 存储与引擎强耦合，无需额外间接层 |
| 交互层实现 | ✅ UINode + Streamlit 分离 | 职责分离，可测试性更好 |

## 二、设计原则

### 2.1 核心设计理念

| 原则 | 说明 | 实现方式 |
|------|------|---------|
| **计算下推** | 尽可能将计算推送到数据库执行 | 表达式 → SQL 编译引擎 |
| **无感切换** | 研究员无需关心底层存储 | 统一 Factor 抽象层 |
| **渐进增强** | 新老代码可共存，逐步迁移 | Adapter 模式 + 接口兼容 |
| **AI 原生** | AI 能力不是插件而是核心 | 各层预留 AI 扩展点 |
| **可观测性** | 全链路可追踪可调试 | 日志、指标、追踪体系 |

### 2.2 非功能目标

| 目标 | 指标 |
|------|------|
| **性能** | 1000 万行因子计算 < 10 秒 |
| **易用性** | 新手 30 分钟可完成第一个策略回测 |
| **可扩展性** | 新增一种数据库引擎 < 100 行代码 |
| **可维护性** | 核心模块测试覆盖率 ≥ 80% |
| **稳定性** | 核心路径年故障率 < 0.1% |

## 四、核心概念定义

### 4.1 Node：一切计算的基础单元

BaseNode 是所有节点的统一基类。核心契约：`input_data → execute() → output_data`

**配置开关**（子类可覆盖）：
- `_enable_validation`：配置校验（默认开）
- `_enable_stats`：执行统计（默认开）
- `_enable_cache`：结果缓存（默认关）
- `_enable_hooks`：钩子函数（默认开）

**核心方法**：
- `_execute()`：子类实现的核心逻辑（抽象方法）
- `execute()`：统一入口（包含校验、统计、钩子、错误处理）
- `before_execute()` / `after_execute()`：生命周期钩子
- `reset()`：重置节点状态
- `serialize()`：序列化（详见 `08-节点序列化方案.md`）

### 4.2 Pipeline：唯一的组合原语

Pipeline 本身也是一个 Node（组合模式），可以嵌套使用。

**三种核心组合原语**：
1. **Pipeline** - 线性管道：按顺序执行节点列表
2. **Parallel** - 并行分叉：所有分支接收相同输入，并行执行，返回字典
3. **Join** - 聚合组合：接收字典输入，通过用户函数聚合为单个输出

**DSL 语法糖**：使用 `>>` 运算符表示线性管道
```python
Pipeline([A, B, C]) == A >> B >> C
```

### 4.3 控制流：三层混合架构

```
┌─────────────────────────────────────┐
│  用户层：专用控制流节点（推荐）       │
│  IfNode / MapNode / WhileNode       │  ← 95% 场景使用
├─────────────────────────────────────┤
│  语法糖层：Pipeline 链式 API         │
│  p.if_then().map().while_loop()    │
├─────────────────────────────────────┤
│  核心层：Expression DSL             │
│  fn(data, ctx) → result             │  ← 可序列化的条件/循环表达式
└─────────────────────────────────────┘
```

> **注意**: Expression DSL 的设计详见 `07-逻辑节点去Lambda化方案.md`。

## 五、BaseNode 基类详细设计

### 5.1 基类核心特性

BaseNode 是一个统一的基类（单体设计），包含以下核心特性：

| 特性分类 | 必选/可选 | 实现方式 | 说明 |
|---------|-----------|---------|------|
| **身份标识** | ✅ 必选 | `name`, `node_id` | 唯一标识，用于追踪和调试 |
| **状态管理** | ✅ 必选 | `state = idle/running/success/failed` | 执行生命周期 |
| **配置存储** | ✅ 必选 | `_config` + Pydantic Schema | 类型安全的配置 |
| **输入/输出 Schema** | ⚠️ 可选 | `input_schema`, `output_schema` | 数据契约 |
| **统一执行入口** | ✅ 必选 | `execute()` | 所有节点共用入口 |
| **配置校验** | ✅ 必选 | `validate()` | 执行前校验 |
| **异常处理** | ✅ 必选 | 统一 try/except + 重试装饰器 | 错误上下文 |
| **日志记录** | ✅ 必选 | `self.logger` | 节点级日志器 |
| **执行统计** | ⚠️ 可选 | `_stats: dict` | 执行次数、耗时、数据量 |
| **结果缓存** | ⚠️ 可选 | `@file_cache` 集成 | 可开关的缓存 |
| **钩子函数** | ⚠️ 可选 | `before_execute`, `after_execute` | 扩展点 |
| **上下文管理** | ⚠️ 可选 | `__enter__`, `__exit__` | with 语句支持 |

> **序列化**: `serialize()` / `deserialize()` 方法由 `Serializable` Mixin 提供，详见 `08-节点序列化方案.md`。

### 5.3 完整接口定义

```python
class NodeState(str, Enum):
    IDLE = "idle"
    RUNNING = "running"
    SUCCESS = "success"
    FAILED = "failed"

class BaseNode(QuantNodesBase, ABC):
    _enable_validation: bool = True
    _enable_stats: bool = True
    _enable_cache: bool = False
    _enable_hooks: bool = True

    def __init__(self, name: str = None, config: Dict[str, Any] = None, **kwargs):
        self.name = name or self.__class__.__name__
        self.node_id = f"{self.name}_{uuid.uuid4().hex[:8]}"
        self.state: NodeState = NodeState.IDLE
        self.logger = logging.getLogger(f"node.{self.node_id}")
        self.stats = NodeStats() if self._enable_stats else None

    @abstractmethod
    def _execute(self, input_data: T = None, **kwargs) -> R:
        """子类实现的核心执行逻辑"""
        pass

    def execute(self, input_data: T = None, *, validate_input: bool = None, **kwargs) -> R:
        """统一执行入口"""
        # 包含校验、统计、钩子、错误处理
        pass
```

### 5.4 性能影响评估

| 操作 | 无基类开销 | 有基类开销（全开） | 性能模式 |
|------|-----------|-------------------|---------|
| 空执行 | 0.03 µs | 5.0 µs | 0.15 µs |
| Pydantic 校验 | - | 2.5 µs | 可关闭 |
| 日志记录 | - | 0.8 µs | 可关闭 |
| 统计更新 | - | 0.3 µs | 可关闭 |
| 钩子执行 | - | 0.2 µs | 可关闭 |

**优化措施**：
- 性能模式开关：关闭 validation/stats/hooks
- `__slots__` 减少内存占用
- 条件分支编译（死代码消除）

## 六、现有功能迁移规划

### 6.1 迁移原则

| 原则 | 说明 |
|------|------|
| **渐进式** | 先迁移非核心节点，验证稳定后再迁移核心节点 |
| **向后兼容** | 保留原有 API，添加 deprecation warning |
| **双轨运行** | 新旧代码可混合使用，逐步替换 |
| **先易后难** | 从简单节点开始，积累经验后处理复杂节点 |

## 七、符号计算引擎设计

### 7.1 核心决策：内联透明化

符号计算**不暴露**为独立节点，而是作为 FactorNode 的后端实现。用户只需要写因子表达式，不需要了解编译过程。

### 7.2 三层架构

1. **Layer 1 用户 API**：`FactorNode("(close - open) / open")` - 用户只需要写表达式
2. **Layer 2 调度与缓存**：表达式解析缓存、引擎自动选择路由、结果缓存策略
3. **Layer 3 后端实现**：符号编译后端 + Pandas 回退后端

## 八、AI 元节点设计

> **详细实现**: Agent 系统的完整架构、工具体系、MCP 协议、并发设计等详见 `13-Agent架构设计.md`。本章仅描述 AI 层在整体架构中的定位。

### 8.1 核心思想

**AI 不处理数据，而是操纵其他节点**。这是与传统"AI 作为处理节点"的本质区别。

### 8.2 StrategyGenerator

**输入**：自然语言描述字符串  
**输出**：可执行的 Pipeline 对象

工作流程：
1. LLM 生成 Pipeline 的结构化定义（JSON）
2. 安全校验
3. 反序列化为可执行的 Pipeline 对象

### 8.3 PipelineOptimizer

优化现有 Pipeline 的执行计划：
1. 公共子表达式提取
2. 节点重排序
3. 并行度自动调整
4. 缓存策略自动配置

## 十一、附录：设计模式应用

| 模式 | 应用场景 |
|------|---------|
| **访问者模式 (Visitor)** | SQL 编译器遍历表达式 AST |
| **策略模式 (Strategy)** | 数据库 Dialect 方言、路由决策规则 |
| **装饰器模式 (Decorator)** | 风控规则堆叠、缓存装饰器 |
| **抽象工厂 (Abstract Factory)** | LLM 客户端、数据库引擎创建 |
| **适配器模式 (Adapter)** | 兼容旧版 factor_table 接口 |
| **建造者模式 (Builder)** | 回测引擎、策略的复杂配置 |
| **观察者模式 (Observer)** | 订单成交事件、策略信号通知 |
