2026-06 期间，QuantNodes 经历了一轮设计模式应用 + 代码审计。起因是：
- `group_analyzer_node.py` 的 `_calc_group_return` 在 bool/discrete 因子下崩 `ValueError`

本文档分两部分：
1. **已应用的设计模式 (Phase 1 + 2)** — 5 个 pattern 落地，~75 个新测试

### 3.3 Abstract Factory 调研结论

> **调研发现**: 抽象工厂在 QuantNodes 适用度有限。判断标准是"是否存在**一族互相依赖**的对象需要在运行时整体切换？"

| 候选 | 是否"一族互相依赖" | 结论 |
|---|---|---|
| 6 个 DataSource (SQLite/DuckDB/MySQL/...) | ❌ 互斥替代品 | Simple Factory 即可 |
| 3 个 Operator Registry (L0/L1/L2) | ⚠️ 分层但**每层独立** | Facade 即可 |
| 4 个 LLM Provider (OpenAI/Anthropic/Local/Mock) | ❌ 互斥替代品 | Simple Factory |

**结论**: 真正适用 Abstract Factory 的场景不存在于 QuantNodes。改用 **Facade + 3 个 Simple Factory** 统一 operator 查询 (即 §3.2 第 3 行的简化版)。

> **Phase 3.2 落地 (2026-06-22)**: `operators/facade.py` 的 `OperatorFacade` /
> `operator_facade` 单例统一了 L0/L1/L2 三层的**只读查询** (`resolve` /
> `get_composite` / `exists` / `kind` / `list_all`)，全部委托既有函数保持
> bitwise 兼容。写路径 (注册) 不收敛，保持各层隔离语义。

### 3.4 不推荐立即动

- **MVC / Service Locator (Enterprise)**: 项目无 GUI 层
- **Prototype (Cache-as-instance)**: 需 profiling 证据

### 3.5 Phase 3.3: Factory + Adapter + DataSource ABC (✅ 完成, `39eaf83`)

> **背景修正**: §3.2 原表曾写"统一 H5/CSV/Parquet 接入 `BaseDBNode`"。
> 调研后否定该方向——`BaseDBNode` 是 **SQL 语义** (`query(sql)`)，而
> `DataLoader` 是 **面板矩阵语义** (`load_factor` / `add_index` /
> `get_axis`)，强行合并会泄漏抽象。改为引入**最小化顶层 `DataSource`
> ABC** 让两个子树各自保留专用接口。同时澄清：`MarketDataCacheNode`
> 对后端无硬限制 (接收外部 `node`)，真正的缺口是 csv/parquet 文件源
> 在 `config_backtest._load_data` 走了 `_read_data_file` 旁路。

**调研发现 (逐行核对)**:

| 子系统 | 文件 | 现状 | 代码味道 |
|---|---|---|---|
| A. DataLoader (文件) | `research/factor_test/utils/data_loader.py` | 普通类、无 ABC，按扩展名 if/elif 分发两处 (`load_factor` / `load_custom`) | parquet 孤儿 (已修, `b83e9d3`)；扩展名分发硬编码 |
| B. database_node (DB) | `database_node/base.py` | `BaseDBNode(ABC)` 已是完整 Adapter，6 后端实现 | 包内无 factory；实例化散落在 `config_backtest._build_db_node` / `_build_embedded_node` |

**落地方案 (3 块)**:

1. **顶层 `DataSource` ABC** (`core/data_source.py`, 新增): 最小化标记基类，
   仅统一 `close()` 生命周期 + `__enter__/__exit__` + "产出 pd.DataFrame"
   语义约定。`BaseDBNode` 继承之并加 `close()` 默认实现 (委托
   `disconnect()`，纯增量)；`FileFormatLoader` 继承之。
2. **DB 节点工厂** (`database_node/factory.py`, 新增): `create_db_node(source,
   **params)` + 注册表 `register_db_node` / `available_sources`。
   `config_backtest._build_db_node` / `_build_embedded_node` 保留方法名、
   内部委托工厂 (解析 conn.ini / path 的逻辑仍留在调用方)。
3. **文件格式 Adapter** (`research/factor_test/utils/file_loaders.py`, 新增):
   `FileFormatLoader(DataSource, ABC)` + `H5Loader/CSVLoader/NPYLoader/
   ParquetLoader` + `build_file_loader(ext)` registry。`DataLoader` 的
   `load_factor` / `load_custom` 分发委托工厂；公共方法签名/输出 bitwise
   不变；H5 经 `store_getter` 回调复用 `_h5_stores` 缓存 (保 Phase H3 优化)。

**兼容性红线**: DataLoader 公共方法 + 各 DBNode 构造/query/connect 行为/输出
bitwise 不变；新工厂/adapter/ABC 全为新增；`config_backtest` 仅等价委托替换。

**不做** (本 Phase 排除): csv/parquet 旁路统一 (`_read_data_file` vs
CSVNode/ParquetNode)，因 polars `LazyFrame` 与 pandas 语义差异需单独评估。

> `run_evolution_e2e._build_config` 37 行嵌套构造。

**落地**: 新增 `QuantNodes/research/factor_test/config_builder.py`:

- `SingleFactorTestConfigBuilder` 流式 API:
  `.factor() / .dates() / .sample() / .preprocess() / .neutralize() /

## 4. 模式选择决策树 (未来参考)

当遇到代码味道时，按此决策树选模式：

| 场景 | 候选模式 | 选哪个？ |
|---|---|---|
| `if x is None: return default` 散落多处 | Null Object | ✅ Null Object |
| 同一接口多算法可互换 (e.g. preprocess / dispatch) | Strategy | ✅ Strategy |
| 算法步骤可拆分并按需组合 (e.g. neutralize chain) | Chain of Responsibility | ✅ Chain |
| 同一对象多装饰需求 (e.g. LLM retry/log/cache) | Decorator | ✅ Decorator |
| 一族互相依赖的产品族 | Abstract Factory | ⚠️ QuantNodes 无此场景 |
| 创建/构造过程多步骤多配置 | Builder | ✅ Builder |
| 跨类统一处理结构树 (e.g. spec / AST) | Visitor | ✅ Visitor |
| 复杂 if/elif 派发到 handler | Command | ✅ Command |
| 一族替代品 (e.g. DataSource / LLM provider) | Factory | ✅ Simple Factory |
| 跨模块共享 cache / connection | Singleton / Flyweight | ⏳ 需 profiling |
| 系统分层: 客户端 ↔ 子系统 | Facade | ✅ (与 Simple Factory 配合) |

**关键 takeaway**: 设计模式不是"找到就能用", 而是要**先识别代码味道 (pain point)**, 然后**用 SOLID 原则判断适用度**。本项目 Phase 1+2 的成功在于:
1. Null Object / Decorator 解决**横切关注** (LLM 调用, 日志, 缓存)
2. Strategy / Chain 解决**算法可扩展性** (新预处理/中性化类型无需改 _execute)
3. Builder / Visitor / Decorator(reg) 解决**代码重复** (报告拼接 / spec 遍历 / 路由表维护)
