## 1. 全市场性能基准 (5397 只股票, 1.36M 行, 2023-07-01 ~ 2024-07-19)

### 1.1 各阶段耗时分布

| 阶段 | 耗时 | 占比 | 说明 |
|------|------|------|------|
| ClickHouse 查询 | 2.5-3.4s | 15-17% | HTTP 接口, ORDER BY ts_code, trade_date |
| Pandas 转换 | <0.01s | <0.1% | rename + type cast |
| Polars 因子计算 | <0.01s | <0.1% | ts_mean/ts_std/ts_lag 等 |
| Polars collect | <0.01s | <0.1% | LazyFrame → DataFrame |

| **_build_equity_curve** | **0.5-1.0s** | **3-5%** | 逐日权益回放 |
| **_compute_statistics** | **1.5-2.5s** | **10-15%** | 绩效统计计算 |
| **总计** | **15-22s** | 100% | |

### 1.2 性能瓶颈分析

#### 瓶颈1: ExecutionBrokerNode (50-70%)

**优化前**: 每笔订单对 DataFrame 做 `quote_data[quote_data['Code'] == code]` 过滤, O(N) per order → O(N²) total

**优化后**: 
- 预构建 `{code: {date: price}}` 嵌套字典, O(1) 查找
- numpy 向量化价格查找 + 费用计算
- 仍然需要逐笔执行(现金依赖), 但查找从 O(N) 降到 O(1)

**性能提升**: 100 stocks: 25s → 0.4s (62x), 2000 stocks: >10min → 5s

#### 瓶颈2: ConfigStrategyNode (6-8%)

**优化前**: `iterrows()` 逐行遍历 DataFrame

**优化后**: 
- 先 `mask = signal != 0` 过滤非零信号 (通常只占 30-50%)
- 用 numpy 数组批量创建 Signal 对象

#### 瓶颈3: _compute_statistics (10-15%)

- `_build_equity_curve` 中 `trades_df.sort_values("dt").to_dict("records")` 对大数据集较慢
- 日期匹配 bug 已修复 (`str(d)[:10]` 统一格式)

## 2. 进一步优化方案

### 2.1 ClickHouse Native 接口 (预期提升 3-5x)

**现状**: HTTP 接口 (requests.post), 每次查询建立新连接

**方案**: 使用 `clickhouse-driver` (native TCP 接口)

```python
# 当前
import requests
resp = requests.post(f"http://{host}:{port}", params={"query": sql})

# 优化后
from clickhouse_driver import Client
client = Client(host=host, port=port, user=user, password=passwd, database=database)
df = client.query_dataframe(sql)
```

**优势**:
- TCP 连接复用, 无 HTTP 开销
- 支持管道化查询
- 数据直接转 Pandas, 无中间序列化

**预期**: CH 查询从 2.5-3.4s → 0.5-1.0s

### 2.2 Polars LazyFrame 全链路 (预期提升 2-3x)

**现状**: Polars → Pandas → 回测引擎

**方案**: 
1. 回测引擎用 Polars 原生 API 重写
2. 或者: Polars LazyFrame 保持到最后, 只在需要时 collect

**关键改动**:
- `ConfigStrategyNode._generate_signals()`: 用 Polars `filter` + `with_columns`
- `ExecutionBrokerNode._execute_orders()`: 用 Polars `join_asof` 做价格查找
- `_build_equity_curve()`: 用 Polars `group_by_dynamic` 逐日聚合

### 2.3 并行计算 (预期提升 2-4x)

## 3. 增量更新机制设计

### 3.1 核心思想

缓存已查询的数据到本地 Parquet 文件, 后续只查询新增部分, 合并后使用。

### 3.2 数据结构设计

```
cache/
├── quote.cn_stock/
│   ├── metadata.json          # 缓存元数据
│   ├── data_20230701_20231231.parquet  # 分段缓存
│   └── data_20240101_20240719.parquet
```

**metadata.json**:
```json
{
  "table": "quote.cn_stock",
  "last_update": "2024-07-19T10:00:00",
  "date_range": ["2023-07-01", "2024-07-19"],
  "total_rows": 1359463,
  "cache_files": [
    "data_20230701_20231231.parquet",
    "data_20240101_20240719.parquet"
  ],
  "query_hash": "abc123..."
}
```

### 3.3 增量查询流程

```python
class IncrementalDataLoader:
    def load(self, config: DataConfig) -> pl.LazyFrame:
        cache_dir = self._get_cache_dir(config)
        metadata = self._load_metadata(cache_dir)
        
        if metadata is None:
            # 首次查询: 全量加载并缓存
            lf = self._full_query(config)
            self._save_cache(lf, config)
            return lf
        
        # 检查是否需要增量更新
        last_date = metadata["date_range"][1]
        today = datetime.now().strftime("%Y-%m-%d")
        
        if last_date >= today:
            # 缓存已是最新, 直接读取
            return self._read_cache(cache_dir, config)
        
        # 增量查询: 只查新增部分
        new_filter = f"WHERE trade_date > toDateTime('{last_date}')"
        new_data = self._query_with_filter(config, new_filter)
        
        # 合并并更新缓存
        self._append_cache(new_data, cache_dir, metadata)
        
        # 返回完整数据
        return self._read_cache(cache_dir, config)
```

### 3.4 缓存失效策略

| 策略 | 触发条件 | 行为 |
|------|---------|------|
| TTL 过期 | `last_update + ttl < now` | 重新全量查询 |
| schema 变更 | 表结构变化 | 重新全量查询 |
| 手动刷新 | 用户指定 `force_refresh=True` | 重新全量查询 |
| 增量追加 | `last_date < today` | 只查新增部分 |

### 3.5 实现建议

1. **缓存目录**: `~/.quantnodes/cache/{source}/{database}.{table}/`
2. **缓存格式**: Parquet (列式存储, 高压缩比)
3. **缓存粒度**: 按月分段 (便于增量更新)
4. **过期策略**: 默认 7 天 TTL, 可配置
5. **并发安全**: 文件锁 + 原子写入 (先写临时文件再 rename)

### 3.6 预期性能提升

| 场景 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 首次全量查询 | 3.0s | 3.0s | - |
| 日常增量 (1天新增) | 3.0s | 0.1s | 30x |
| 周度增量 (5天新增) | 3.0s | 0.3s | 10x |
| 月度增量 (22天新增) | 3.0s | 0.8s | 4x |
