## 一、系统定位

QuantNodes 是一个 **Agent 驱动的量化研究平台**，核心理念：

- Agent 理解用户需求，自动完成策略研发全流程
- 通过配置（YAML + conn.ini）驱动回测，无需手写代码
- 知识库持续积累，策略/因子/研报形成可复用的知识资产

---

## 二、三大核心功能

### 功能1: Agent 驱动的策略回测

**用户场景**: "帮我写一个双均线策略，回测一下看看效果"

**完整链路**:

```
用户需求 → Agent 理解需求
  ├── 搜索 Wiki: 是否已有类似策略/因子?        ← LLMWikiFy
  ├── 读取数据: ClickHouse / CSV / Parquet     ← database_node + config
  ├── 生成策略: YAML 配置                       ← ConfigBacktestTool
  ├── 执行回测: ConfigBacktestRunner            ← 回测引擎
  ├── 生成报告: Markdown 分析报告               ← LLMWikiFy
  └── 保存 Wiki: 策略页面 + 回测结果            ← LLMWikiFy
```

**缺口**: 数据层断裂（database_node 未接入 config 管线）— executor/runner 硬编码列名已修复（见 `07-执行清单.md` 第二节）

### 功能2: 策略监控与优化

**用户场景**: "监控这个策略的样本外表现，如果跑偏了就优化"

**缺口**: 调度层空白、监控层空白、版本管理层空白

### 功能3: 量化研究

功能3 拆分为三个子功能：

| 子功能 | 定位 | 优先级 |
|--------|------|--------|
| **功能3A: 构建因子库** | Wiki 代理层基础设施 | 最高 |
| **功能3B: 研报复现** | 从研报提取逻辑并验证 | 中 |
| **功能3C: AutoResearch** | 基于 LLM 自动挖掘因子 | 中 |

**功能3A 是基础设施**，功能3B 和 功能3C 依赖它存储因子/逻辑到 Wiki。

### 7.3 关键设计决策：两层列名设计

**问题**: `date_column` 和 `code_column` 原本同时用于 SQL `ORDER BY`（需要数据库原始名）和 executor 过滤（需要映射后名字），当 `column_mapping` 非空时产生冲突。

**方案**: 拆分为两层：

```yaml
data:
  # 数据库层（用于 SQL 查询）
  db_date_column: trade_date
  db_code_column: ts_code
  
  # 内部标准层（用于 executor/backtest）
  date_column: date
  code_column: code
  
  # 映射关系
  column_mapping:
    ts_code: code
    trade_date: date
    vol: volume
```

### 7.4 数据流全链路图

```
YAML 配置 (data.source: clickhouse)
    ↓
_build_query() - 使用 db_* 字段
    ↓
ClickHouse 返回 DataFrame: [ts_code, trade_date, open, ...]
    ↓ column_mapping
DataFrame: [code, date, open, high, low, close, volume]
    ↓
ConfigExecutor - 因子计算 + 日期/股票筛选
    ↓
ConfigBacktestRunner._normalize_columns()
    ↓
回测引擎 (ConfigStrategyNode → ExecutionBrokerNode → BacktestResult)
```

## 八、全市场性能分析与优化

### 8.1 各阶段耗时分布 (5397 只股票, 1.36M 行)

| 阶段 | 耗时 | 占比 | 说明 |
|------|------|------|------|
| ClickHouse 查询 | 2.5-3.4s | 15-17% | HTTP 接口, ORDER BY ts_code, trade_date |
| Pandas 转换 | <0.01s | <0.1% | rename + type cast |
| Polars 因子计算 | <0.01s | <0.1% | ts_mean/ts_std/ts_lag 等 |
| **ConfigStrategyNode** | **1.0-1.5s** | **6-8%** | signal 过滤 + Order 对象创建 |
| **ExecutionBrokerNode** | **8-15s** | **50-70%** | 订单执行 + 价格查找 + 费用计算 |
| **_build_equity_curve** | **0.5-1.0s** | **3-5%** | 逐日权益回放 |
| **_compute_statistics** | **1.5-2.5s** | **10-15%** | 绩效统计计算 |
| **总计** | **15-22s** | 100% | |

### 8.2 性能瓶颈分析

1. **ExecutionBrokerNode 是主要瓶颈** (50-70%) — 订单执行、价格查找、费用计算
2. **ClickHouse 查询是次要瓶颈** (15-17%)
3. **因子计算本身极快** (<0.1%)

### 8.3 优化建议

1. **ClickHouse 查询优化**: 使用 `query_filter` 缩小数据范围
2. **ExecutionBrokerNode 优化**: 批量处理订单，减少循环
3. **缓存**: 用 Parquet 缓存行情数据，避免重复查询

## 九、MarketDataCacheNode 缓存规划

### 9.1 当前问题

全市场回测 (5397 只股票, 1.36M 行) 每次执行都需要:
- ClickHouse HTTP 查询: 2.5-3.4s
- 数据转换 + 因子计算 + 回测: 12-19s
- **总计: 15-22s**

### 9.2 目标

创建 `MarketDataCacheNode`，用 Parquet 文件缓存行情数据:
- 缓存命中时跳过 ClickHouse 查询 (节省 2.5-3.4s)
- 支持增量更新 (只查新增日期)
- 支持 TTL 过期策略
- 继承 `BaseNode`，支持 Pipeline (`>>`) 链式调用

### 9.3 架构设计

```
MarketDataCacheNode
├── _cache_dir: str              # 缓存目录
├── _ttl_days: int              # TTL 天数
├── _last_update: Optional[date] # 最后更新时间
│
└── execute(input_data):
    ├── 检查缓存是否存在
    ├── 检查是否过期 (_ttl_days)
    ├── 检查增量更新 (只查 last_update 之后的数据)
    ├── 更新缓存
    └── 返回缓存的 DataFrame
```

## 十一、功能3A：构建因子库 (Factor Library)

### 11.1 定位

因子库的**基础设施层**，其他功能依赖此层存储因子/逻辑到 Wiki。

### 11.2 Wiki 代理层

```python
# QuantNodes/research/wiki.py

class WikiFactorProxy:
    """Wiki 因子库代理层 - 封装 llmwikify 调用"""

    def __init__(self, wiki_path: str):
        self.wiki_path = wiki_path  # 本地 Wiki 目录

    def store_factor(self, factor: WikiFactor) -> str:
        """存储因子到 Wiki，返回 page_name"""

    def get_factor(self, name: str) -> Optional[WikiFactor]:
        """获取因子，不存在返回 None"""

    def search_factors(self, query: str, limit: int = 10) -> List[WikiFactor]:
        """搜索因子"""

    def list_factors(self, source=None, category=None, tags=None, limit=50) -> List[WikiFactor]:
        """列举因子（支持过滤）"""

    def update_factor(self, name: str, updates: Dict) -> bool:
        """更新因子字段"""

    def delete_factor(self, name: str) -> bool:
        """删除因子"""

    def store_logic(self, logic: WikiLogic) -> str:
        """存储研报逻辑"""

    def get_logic(self, name: str) -> Optional[WikiLogic]:
        """获取逻辑"""

    def add_relation(self, source_name: str, target_name: str, relation: str) -> bool:
        """添加关系: uses / correlates_with / derived_from"""

    def get_neighbors(self, name: str) -> List[Dict]:
        """获取关联节点"""
```

### 11.3 数据模型

```python
# WikiFactor - 因子数据
```

## 十二、功能3B：研报复现

### 12.1 用户场景

### 12.2 核心能力

| 模块 | 功能 | 说明 |
|------|------|------|
| **PDF解析** | 复用 llmwikify | 提取文本、表格、公式 |
| **逻辑提取** | LLM 提取逻辑 | 不一定是因子，可以是规则、条件、公式等 |

### 12.3 提取内容类型

```
研报复现提取的"逻辑"类型:
├── 因子公式: "close / close.shift(20) - 1"
├── 交易规则: "金叉买入，死叉卖出"
├── 仓位规则: "根据波动率调整仓位"
├── 筛选条件: "市值 > 100亿 且 ROE > 10%"
└── 组合规则: "等权配置前20只股票"
```

### 12.4 数据流

```
研报PDF → llmwikify 解析 → 文本/表格/公式
                                    ↓
                          LLM 逻辑识别
                                    ↓
                          存入 Wiki (Logic Library)
                                    ↓
                          逻辑验证 (可能涉及因子计算)
                                    ↓
                          对比报告 → 存入 Wiki
```

```yaml
    page: string
```
