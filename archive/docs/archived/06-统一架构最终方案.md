## 一、架构现状诊断与决策

### 1.1 原方案冲突分析

项目启动时存在两个并行的重构方案：

| 方案 | 核心思路 | 周期 |
|------|---------|------|
| **方案 A**：6 层分层架构 | 存储层 → 数据访问 → 业务逻辑 → 符号计算 → AI 层 → 交互层 | 35 天 |
| **方案 B**：统一节点架构 | BaseNode → 各种节点子类 → Pipeline 组合 | 9-10 周 |

### 1.2 ✅ 最终决策：**两者完全兼容，统一为三层架构**

| 原方案 A（分层） | 原方案 B（节点） | **统一架构定位** |
|-----------------|-----------------|-----------------|
| 存储引擎层 | ClickHouse/MySQL Dialect | **内置于 DatabaseNode**<br>不单独抽象，通过 dialect 区分引擎 |
| 数据访问层 | DatabaseNode | **DatabaseNode**<br>连接池 + 查询执行 + 路由 |
| 业务逻辑层 | FactorNode/OperatorNode | **FactorNode/TransformNode**<br>核心业务逻辑 |
| 符号计算层 | （方案 B 未明确） | **FactorNode 的内部实现**<br>对用户透明，不暴露为独立节点 |
| AI 增强层 | StrategyGenerator | **元节点（Meta-Node）**<br>不处理数据，而是生成 Pipeline |
| 交互层 | （方案 B 未考虑） | **UINode + Streamlit 分离**<br>UINode 准备数据，Streamlit 负责渲染 |

### 2.2 设计原则

1. **最小侵入** - 不强制子类实现过多方法
2. **性能友好** - 热路径开销可控，可开关高级功能
3. **渐进迁移** - 支持新旧代码混合运行
4. **机制与策略分离** - 通用执行在底层，控制流语义在上层
5. **AI 原生** - AI 作为元节点，动态构建 Pipeline

## 三、核心概念定义

### 3.1 Node：一切计算的基础单元

BaseNode 是所有节点的统一基类。核心契约：`input_data → execute() → output_data`

**配置开关**（子类可覆盖）：
- `_enable_validation`：配置校验（默认开）
- `_enable_stats`：执行统计（默认开）
- `_enable_cache`：结果缓存（默认关）
- `_enable_hooks`：钩子函数（默认开）

**核心方法**：
- `_execute()`：子类实现的核心逻辑（抽象方法）
- `execute()`：统一入口（包含校验、统计、钩子、错误处理）
- `before_execute()` / `after_execute()`：生命周期钩子
- `reset()`：重置节点状态
- `to_dict()`：序列化

### 3.2 Pipeline：唯一的组合原语

Pipeline 本身也是一个 Node（组合模式），可以嵌套使用。

**三种核心组合原语**：
1. **Pipeline** - 线性管道：按顺序执行节点列表
2. **Parallel** - 并行分叉：所有分支接收相同输入，并行执行，返回字典
3. **Join** - 聚合组合：接收字典输入，通过用户函数聚合为单个输出

**DSL 语法糖**：使用 `>>` 运算符表示线性管道

```python
Pipeline([A, B, C]) == A >> B >> C
```

## 四、控制流节点设计

### 4.1 核心决策：三层混合架构

```
┌─────────────────────────────────────┐
│  用户层：专用控制流节点（推荐）       │
│  IfNode / MapNode / WhileNode       │  ← 95% 场景使用
├─────────────────────────────────────┤
│  语法糖层：Pipeline 链式 API         │
│  p.if_then().map().while_loop()    │
├─────────────────────────────────────┤
│  核心层：通用 _LogicNode（内部原语）│
│  fn(data, ctx) → result             │  ← 框架内部 + 高级用户
└─────────────────────────────────────┘
```

### 4.2 专用控制流节点 API

#### IfNode - 条件分支

如果条件满足，执行 true_branch，否则执行 false_branch（可选）

#### MapNode - 分块映射

对输入数据按 group_by 规则分组，对每组执行相同节点，支持并行。

#### WhileNode - 条件循环

只要条件满足，就循环执行 body，支持最大迭代次数防止死循环。

### 4.3 不做通用 LogicNode 作为主 API 的原因

| 维度 | 纯通用节点 | 专用节点 | 混合架构 |
|------|-----------|---------|---------|
| 可观测性 | ⭐⭐（黑盒） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 可序列化 | ⭐（不可） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| AI友好性 | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 工程化 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |

**综合评分**：纯通用节点 6/10，专用节点 9/10，混合架构 10/10

## 五、符号计算引擎设计

### 5.1 核心决策：内联透明化 ✅

符号计算**不暴露**为独立节点，而是作为 FactorNode 的后端实现。用户只需要写因子表达式，不需要了解编译过程。

**类比**：Python 解释器把 .py 编译成字节码，用户不需要知道编译过程。

### 5.2 三层架构

1. **Layer 1 用户 API**：`FactorNode("(close - open) / open")` - 用户只需要写表达式
2. **Layer 2 调度与缓存**：表达式解析缓存、引擎自动选择路由、结果缓存策略
3. **Layer 3 后端实现**：
   - 符号编译后端：编译表达式为数据库 SQL
   - Pandas 回退后端：复杂表达式在本地计算

### 5.3 自动引擎选择

根据表达式复杂度自动选择：
- 简单表达式 → Symbolic 后端（下推到数据库执行）
- 复杂表达式 → Pandas 后端（本地计算）

用户也可以显式强制使用某个引擎。

## 六、AI 元节点设计

### 6.1 核心思想

**AI 不处理数据，而是操纵其他节点**。这是与传统"AI 作为处理节点"的本质区别。

### 6.2 StrategyGenerator - 策略生成器

**输入**：自然语言描述字符串  
**输出**：可执行的 Pipeline 对象

工作流程：
1. LLM 生成 Pipeline 的结构化定义（JSON）
2. 安全校验
3. 反序列化为可执行的 Pipeline 对象

### 6.3 PipelineOptimizer - 管道优化器

优化现有 Pipeline 的执行计划：
1. 公共子表达式提取
2. 节点重排序（把过滤条件前置）
3. 并行度自动调整
4. 缓存策略自动配置

## 八、最终决策总结表

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 两个原方案关系 | ✅ 统一为三层架构 | 分层架构是节点分类的依据，Pipeline 是组合方式 |
| 控制流实现 | ✅ 三层混合架构 | 专用节点保证可观测性，通用节点提供灵活性 |
| 符号计算暴露方式 | ✅ FactorNode 内部透明实现 | 降低用户认知负担，简化API |
| AI 层定位 | ✅ 元节点（生成 Pipeline） | 发挥 AI 优势，不做数据处理 |
| 组合原语 | ✅ Pipeline/Parallel/Join | 覆盖 99% 的量化场景，简单通用 |
| 存储层抽象 | ✅ 内置于 DatabaseNode | 存储与引擎强耦合，无需额外间接层 |
| 交互层实现 | ✅ UINode + Streamlit 分离 | 职责分离，可测试性更好 |
